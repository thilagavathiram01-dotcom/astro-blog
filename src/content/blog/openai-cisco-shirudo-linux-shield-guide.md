OpenAI and Cisco launched Shirudo on November 23, 2026. This open-source runtime lets teams protect running Linux systems while permanent patches are prepared and tested. Shirudo uses temporary shields to block vulnerable code paths without forcing a restart.<grok type="render_inline_citation" citation_id="288" />

The gap between finding a vulnerability and deploying a tested patch often stretches days or weeks. During that window, systems stay exposed. Shirudo aims to close it by applying targeted protections that leave legitimate traffic flowing.

## What Shirudo Does

Shirudo is Japanese for "shield." It is an open-source project that combines OpenAI's AI capabilities with Cisco's (via Isovalent) eBPF expertise. It builds on Tetragon, rewritten for agent-driven workflows.<grok type="render_inline_citation" citation_id="289" />

In a controlled test, a shield generated by OpenAI's Codex blocked a Java4Shell exploit attempt against a running Elasticsearch service. The service continued without a restart. The shield added an input check to Java's Base64 decoder and attached it to the process.

Shirudo is pre-release. Production use requires a Linux kernel with Shirudo's signed-loader ABI and kernel patches, plus a TPM 2.0 chip. Operators should start with the provided VM quickstart or Isovalent's browser lab.

## How the Shields Work

Shirudo relies on eBPF. This Linux technology runs small, verified programs at specific points inside the kernel or attached to userspace processes. It observes activity and applies protections without changing source code or rebooting.<grok type="render_inline_citation" citation_id="288" />

Four core capabilities define it:

- **Live protection:** Shields block vulnerable paths while the system keeps running. Teams can monitor impact in non-enforcing mode first.
- **Defense at machine speed:** AI agents (such as Codex) investigate vulnerabilities, generate shields, and validate them. Humans approve every deployment.
- **Trusted deployment:** Shields are cryptographically signed. The Linux eBPF verifier checks them before loading. Kernel controls prevent unauthorized changes.
- **Hardware-backed verification:** A Trusted Platform Module records loads and unloads. Operators can verify the protection state later.

Shields are temporary. They retire automatically once the permanent CVE patch ships, avoiding configuration drift.

## Try the VM Quickstart

The official quickstart walks you through building Shirudo, booting a protected test VM with a software TPM, signing a test upatch (micropatch), loading it, attesting the state, and unloading it. Your host acts as the operator; the QEMU VM is the target.<grok type="render_inline_citation" citation_id="288" />

**Prerequisites (summary):** Linux host with KVM (or Lima VM on Mac), unlimited locked memory (`ulimit -l unlimited`), clang/LLVM 23 as `/usr/bin/clang`, OpenSSL 3.5+, development packages for libelf, zlib, libcurl, tpm2-tss, and LuaJIT. Also QEMU, swtpm, dracut, Docker or Podman, and related tools. The VM scripts tell you the exact install commands if anything is missing.

Steps (abbreviated from the docs):

1. Clone the repository: `git clone https://github.com/shirudo-dev/shirudo && cd shirudo`
2. Fetch the pinned test kernel: `testing/vm/kernel-artifact.sh fetch`
3. Build: `make` then `make shirudo-build`
4. Export PATH: `export PATH="$PWD:$PWD/tools/shirudo-build:$PATH"`
5. Boot the test VM: `make -C testing vm VM_NAME=quickstart`
6. SSH in: `make -C testing vm-ssh VM_NAME=quickstart`
7. On the target, check status: `shirudo status` (expect Status: ok and all conditions OK)
8. On the operator, sign a test upatch (the basic fixture that attaches to `do_nanosleep` and does nothing): use the generated keys and `shirudo build ...`
9. Load on the target: `shirudo upatch load basic.upatch`
10. Attest and verify the TPM measurement chain, then unload with a signed unload directive.

The test confirms the signed loader is accepted, the program is pinned, and the TPM records the change. Root cannot tamper with Shirudo's state because of the BPF LSM protections.

Isovalent also offers a self-guided browser lab that covers the same concepts without local builds.

## Practical Tips Before You Deploy

Start only in a lab or isolated VM. Shirudo is not production-ready yet. Production targets need the special kernel and a real TPM 2.0.

Always review shields before loading. An exploit and a legitimate request can share the same kernel operation. A poorly scoped shield could disrupt the service. The design includes a monitoring mode for this reason.

Use the attestation flow. After loading, collect evidence from the target and verify it on the operator against the expected chain. This gives cryptographic proof of what is running.

Contribute or watch the project. The code is on GitHub under BSD 2-Clause (BPF programs dual-licensed). A technical webinar is scheduled for December 15, 2026. The Linux Plumbers Conference walkthrough (embedded above) shows the operator/target workflow in detail.

## Conclusion

Shirudo addresses a real operational problem: the time between vulnerability disclosure and safe patch deployment. By combining eBPF live mitigations with AI-generated shields, signed verification, and TPM records, it gives defenders a practical way to reduce exposure without downtime.

The project is early. Treat the current release as a platform for testing and contribution rather than a drop-in production control. Follow the official quickstart, try the lab, and review every shield. As more tested shields become available alongside disclosures, the defender's window can shrink.
